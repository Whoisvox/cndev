# logsvc SLO 宣言 v1

> 状态：**参考稿**（stage4 M0）——标 ⚖️ 的地方是需要你拍板的决策点，我给了选择和理由，你可以推翻，但必须写下你自己的理由。
> 服务：logsvc（godev ns，2 副本，NodePort 30222）
> 数据源：**服务端指标**（对客户端体验的近似，盲区见覆盖范围）
> 评估工具：Prometheus（godev/prometheus-server）
> 成文日期：2026-08-14，基于 28d 回看窗口实测

## 0. 总览

| SLO | SLI（一句话） | 目标 | 窗口 | 当前实测 | 预算状态 |
|---|---|---|---|---|---|
| SLO-1 可用性 | 到达服务端的 /ping 请求中非 5xx 的比例 | ≥ 99.9% | 28d 滚动 | 100% | 未消耗 |
| SLO-2 延迟 | 服务端处理时间 ≤ 5ms 的 /ping 请求比例 | ≥ 99% | 28d 滚动 | 99.71% | 已消耗 29% |

## SLO-1：可用性

- **SLI 定义**：`成功事件 = 状态码非 5xx 的 /ping 请求；坏事件 = 5xx`。比例形式：`1 − 坏事件/总事件`。
- **计算公式**（已在本集群实测，结果 = 1）：
  ```promql
  1 - sum(rate(http_requests_total{path="/ping", status=~"5.."}[28d]))
      / sum(rate(http_requests_total{path="/ping"}[28d]))
  ```
- **目标值：99.9%** ⚖️
  理由：在接受不完美的现实下，尽力保证服务可用，数据来源之前的压测数据，99.9%表示每周不可用的预算时间为10.8分钟。
  依据（两个锚点）：
  1. 实测能力：stage3 压测 200 万请求零失败，28d 回看 5xx = 0（含 CPU 节流、OOM 事故时期也没有 5xx 到达 /ping）；
  2. 留白意图：99.9% 给未来的发布、故障注入实验（M2）留出 10 倍于当前失败率的余量。定 100% = 永远不能做实验；定 99.99% 对无上游依赖的单体服务没有额外意义。
- **窗口**：28d 滚动。
- **Error budget**：`1 − 99.9% = 0.1%`。换算：28d × 24h × 0.1% = **40.3 分钟的「全量请求都坏」等价时长**。
- **覆盖范围**：
  - 只统计业务路径 `/ping`。`/healthz`、`/readyz` 探针失败不算业务坏事件——那是存活/就绪域，靠告警单独处理，混进来会稀释业务信号。
  - **401 / 404 / 405 不算坏事件** ⚖️：客户端错误，服务正确拒绝正是正常行为（本窗口 401 = 9,710 次 ≈ 0.076% 流量，全部是无 token 探测）。**未来若加 429 限流，429 必须算坏**——限流是服务端容量问题，不是用户的错。
  - panic 被 `withRecovery` 兜住的 500 算坏事件。
  - **声明的盲区**：服务端指标看不见连接级失败。stage3 发布零掉包实验里的 `000`（连接被重置）根本没到达服务端，不会出现在任何服务端计数器里。所以本 SLI 测的是「**到达服务端的请求**」的健康度，发布期掉包需要客户端探测/入口侧指标补足——这是「用服务端近似客户端 SLI」的固有代价。
  - **synthetic（实验/压测）流量** ⚖️：三轮故障注入（M2 两次 + M4-3 一次）已证明实验流量会改写账本——预算被烧到 −401，「破产」不是事故而是自己扎的。处理条款见第 5 节；当前按方案 C（事后标注）过渡，目标态方案 B（独立路径）。
- **当前实测**（2026-09-23 更新）：SLI = 59.7%，可用性预算剩余 −401.7（三轮实验烧穿，见第 5 节），延迟预算剩余 0.78。M0 成文时的初值（SLI=1.0、预算满）保留在 git 历史中。

## SLO-2：延迟

- **SLI 定义**：服务端处理时间（handler 耗时，不含网络与排队）≤ 阈值的 /ping 请求比例。
- **计算公式**（阈值 5ms，已实测 = 0.9971）：
  ```promql
  sum(rate(http_request_duration_seconds_bucket{path="/ping", le="0.005"}[28d]))
      / sum(rate(http_request_duration_seconds_count{path="/ping"}[28d]))
  ```
- **阈值选择：5ms** ⚖️ —— 这个数不是拍的，是被三个约束逼出来的：
  1. **桶边界约束**（stage3 教训）：阈值必须落在桶边界上，否则只能线性插值估算。当前桶 `{10µs, 20µs, 250µs, 500µs, 1ms, 2.5ms, 5ms, 10ms}`，候选只有 1ms / 2.5ms / 5ms / 10ms；
  2. **schema 一致性约束**：28d 窗口横跨三代桶方案（见第 3 节），**只有 le=0.005 在所有历史 schema 中都存在**。选 1ms 的话历史数据算出来是 22%——那是假象，不是延迟；
  3. **实测锚点**：压测下服务端 P99 ≈ 249µs，5ms 给 GC 停顿、节点压力、滚动发布留了 20 倍余量。
- **目标值：99%** ⚖️
  为什么不是 99.9%：实测 0.29% 的请求 > 5ms（主要来自 stage3 CPU 256m 节流时代），**99.9% 目标在当前数据下已经违约**（0.29% > 0.1% 预算）。SLO 不能签一份已经破了的合同——先用 99% 站稳，等 M2 之后用干净的压测数据再收紧。
- **窗口**：28d 滚动。
- **Error budget**：`1%` 的请求允许超阈值。当前超标 0.29% → **已消耗 29%，剩余 71%**（≈ 0.71% 的余量可烧）。
- **覆盖范围**：
  - histogram 没有 status label → 本 SLI 统计**所有** /ping 请求（含 401）的延迟，无法只统计成功请求。已接受此局限；若要分离，需给 histogram 加 status label（label 基数代价需评估）。
  - 只测 handler 时间（stage3「延迟的两个真相」）：客户端实测 P99 32ms 与这里的 5ms 不矛盾，差值是排队+网络，归客户端侧 SLO 管，本宣言不覆盖。
  - >10ms 的请求全部落 +Inf 桶，无法细分——阈值最大只能选到 10ms。

## 2. Error budget 盘点（任务 3 的答案）

- **窗口不满**：服务总历史 17d < 28d。处理方式：滚动窗口在数据积累满之前按实际经过时间评估，并在看板上标注「warmup」；28d 满后 SLO 正式生效。这是新服务 SLO 的标准做法，不是作弊。
- **更尖锐的现实**：当前 RS（3d20h 前因 annotation 变更滚动更新）生命周期内 `/ping` **零请求**。今天的 SLO 本质是一份关于过去 12.75M 请求的合同。没有流量，SLI 只是历史读数——这正是 M2 需要故障注入+受控流量的原因。
- **rollout 重置计数器 ≠ 丢历史**：Prometheus TSDB 保留 dead series，`rate/increase` 长窗口能看穿 Pod 生死（本次 28d 数据全部来自已死的旧 Pod）。但要区分两种「断」：
  - 计数器重置（Pod 重建）：长窗口查询**不受影响**；
  - 桶 schema 变更（换镜像）：长窗口比例计算**被污染**（下节）。

## 3. 已知数据质量问题（M1/M2 之前必读）

1. **桶 schema 混杂**：28d 内历经 DefBuckets → 自定义桶 v1（.0005 起）→ v10（.00001 起）。`le="0.001"` 比例实测 22.03% 是**假象**——旧 schema 的序列没有这个桶，不进分子却进分母。任何 < 5ms 的阈值在历史窗口上都不可信。教训：**桶方案变更等价于指标换名**，应在变更时打点记录（recording rule 或 annotation），或只评估变更后的窗口。
2. **counter/histogram 缺口 ≈ 9,836**：最老一代（无 `pod` label）的序列里，counter 比 histogram `_count` 多 ≈9,836 条，与 401 计数（9,710）吻合 → 早期某版中间件把 401 计进了 counter 却没 Observe 进 histogram。影响分母 0.077%，对 SLO 无实质影响。**练习**：翻 git log 找出是哪一版 middleware 造成的。
3. **对账方法**：histogram `_count` ≡ `+Inf` 桶（本窗口均为 12,745,753，分毫不差）——写 SLO 公式前先做这种对账，是防止公式写错的免费保险。

## 5. synthetic（实验）流量条款 —— Q1 的正式回答

**问题**：三轮故障注入把 28d 可用性预算烧到 −401.7。按 SRE 书的纪律「预算烧完 → 冻结发布」，那我是不是该停止一切发布 28 天？显然荒谬——因为烧预算的不是事故，是实验。

**结论：实验流量必须能被识别，否则 SLO 无法区分「系统坏了」和「我们在测系统会不会坏」。**

三个候选方案：

| 方案 | 做法 | 代价 | 判定 |
|---|---|---|---|
| A. 标签区分 | 中间件给指标加 `traffic="user"｜"synthetic"`，SLO 规则加 `traffic!="synthetic"` | 序列数翻倍（每个 label 值组合独立序列）；值域必须有界 | 备选 |
| **B. 独立路径** | 压测打 `/internal/ping`，SLO 只管 `/ping` | stress 工具加个 flag；路由多一条 | **目标态（推荐）** |
| C. 事后标注 | Grafana annotation 标记实验时段，账本不改 | 零工程成本，但账本永远是脏的 | **当前过渡方案** |

**选 B 的理由**：零标签代价（不给 Prometheus 增加任何序列），路径本身就是最明确的意图声明，而且天然支持「synthetic 流量有自己的 SLO」——实验路径也要被测（它得能测出故障），只是不进用户视角的合同。A 方案的问题在于它把「这是实验流量」这个**请求级属性**编码进了**指标的维度空间**，代价是永久性的存储放大；而路径是路由层的天然分区，代价只在请求处理层。

**当前状态（诚实记录）**：本轮实验按方案 C 处理——预算数字是脏的，靠 Grafana annotation + 本文档说明。**不修改历史**：28d 滚动窗口是只读的，这三轮跳水会在各自满 28 天后自然滚出去，届时账本自动恢复干净。

**方案 B 落地前的纪律**（现在生效）：
1. 任何故障注入实验**必须**在 Grafana 打 annotation（时间 + FAIL_RATE 值 + 目的）；
2. 实验前记录当时的预算余额，实验后记录差额——让「烧掉多少」是已知量而不是意外；
3. **实验结束立刻关 FAIL_RATE**（M4-3 实测过一次忘关：告警因流量停止而 resolved，但故障仍活着，一发请求就返回 500——假恢复）；
4. 看板上无法解释的突变一律视为待调查项，不允许「大概是实验吧」这种口头解释过关。
